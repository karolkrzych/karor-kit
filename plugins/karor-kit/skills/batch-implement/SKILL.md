# Batch implement

Orchestrator protocol: N tickets in -> waves of parallel `implement` runs -> merged main, green suite, playtest ask. Per-ticket flow = the `implement` skill (claim, brief, dispatch, review, Cost); this skill adds planning, scheduling, landing.

Output style: Be extremely concise. Sacrifice grammar for the sake of concision. Human sees: wave plan (for approval), 1 line per dispatch, landing report.

1. **Collect**: fetch every ticket — status/assignee rules per `implement` step 1. Fails litmus test -> drop from batch, report, continue with the rest.
2. **Wave plan** — two dependency passes, BOTH mandatory:
   - **Logical**: ticket builds on another's output (sound effect for an entity that doesn't exist yet) -> later wave.
   - **Hotspots**: two tickets editing the SAME FUNCTION/REGION (turn-start upkeep order, one resolve path, one enum block) -> serialize THOSE TWO. Sharing a FILE is not a reason: landing is serialized and the lander's integrate step merges. Evidence: prototype-dnd v5–v8 ran 6-ticket waves with `battle.gd` in most of them, 0 lost landings; batch v9 run 1 cut 12 one-ticket waves by file overlap = 4 tickets in 4 h and ~5M tokens (2026-09-17) — never again. Target 4–6 tickets per wave; count pins / catalogs / balance keys get ONE owner per wave or an explicit union rule in the brief. (The old "file overlap = never same wave" came from 2-day z-garden batches without an integrate step.)
   Present plan (wave -> tickets + reason) -> human OK BEFORE first dispatch.
3. **Execute wave**: claim + dispatch all wave tickets in parallel, one implementer each, model per `m:` label; skeptic model = the ticket's class (`m:sonnet` -> sonnet skeptic, `m:opus`/`m:fable` -> opus; runner `review_model`). Branches cut from CURRENT main. Review each diff per `implement` steps 4-5; PR opened -> In Review.
4. **Land wave** before next starts: merge PRs locally into main, commit message `Merge pull request #N from <owner>/<branch>` — GitHub marks PRs MERGED once main lands. `gh pr merge` = classifier-blocked, don't use. After merges: `--import` step (global `class_name` set changed) + full suite; red -> stop batch, report. Green + pushed -> **tear down every landed ticket's worktree** right away (`git worktree remove <wt>` + `git branch -d <branch>`, per `implement` Rules); dropped/failed tickets keep theirs. Push main YOURSELF — default (Karol, 2026-08-29); invocation forbids it or push blocked by classifier -> hand back: local main ready, human pushes.
5. **Consent in briefs**: say push authorization comes from Karol's own instruction to the orchestrator; implementer still refuses -> fallback "report pushed:false, move on", orchestrator pushes the branch itself. Standard pattern — don't fight for 0 refusals.
6. **Close out**: per ticket Done + `## Cost` dispatch lines IMMEDIATELY at that ticket's Done (wave landing), per `implement`; orchestrator tokens split evenly across batch tickets (`(orchestration, batch/N)`), appended to EVERY batch ticket at batch close-out. **Batch note** -> project's Linear doc `[<project>] Batch log` (create if missing, newest section on top): dated `##` header, ticket table (id + title), "co weszło" summary grouped by theme, end state (main hash, suite result, PR range). Batch NOT closed without human playtest smoke — human plays, feedback -> input for `refinement`. Report: landed tickets, suite result, refusals/flakes, playtest ask. Last act of the batch: `git worktree prune` + remove every helper worktree the batch cut (landing, review, arch — anything under `<wt-root>/` that is not an unlanded ticket or a briefs/notes dir); report what stays on disk and why.

Rules: wave N+1 starts when wave N's LANDING is done — a not-landed ticket does NOT stop the batch (runner `continue-on-partial`): tickets `blocked_by` it are deferred, everything else proceeds, the orchestrator rules in parallel and re-queues it with `resume_findings`. A ruling stop costs 30–40 min of wall-clock, so pre-grant in COMMON/briefs what the issue template calls standing scope (mechanical pins, Balance triple, host class) and treat a documented best-guess default as minor "ruling wanted", never blocking (v9 2026-09-17: 5 of 6 tickets stopped on rule 3 or "needs ruling"). Ticket fails twice -> drop, continue rest, report at end. Blocked Linear write -> split calls (per `implement`). One batch = one session; `implement`'s one-session-one-ticket rule yields here — the batch invocation IS the explicit exception.
